# pirate voyage ゲーム企画書兼仕様書

企画名：黒潮の航海 失われた潮路

対象プロジェクト：ryotamatsuki/pirate-voyage

作成日：2026年9月30日　版：1.0

## 1 企画の結論

pirate-voyage を、未知の海を探索し、交易で船を育て、仲間や港との関係を築く一人用の海洋冒険ゲームへ拡張する。
物語の大目標は、五つの海域に残された観測記録から「失われた潮路」を復元することとする。
航路の調査を進める手段には交易、救助、交渉、海賊行為を用意し、プレイヤーが航海の目的と生き方を選べるようにする。

最初の公開版は、一海域、五港、一隻、五商品、十種類の遭遇、五段階の船の成長、物語第一章に絞る。
次に船員と商船の襲撃、その後に港の影響力と複数海域を追加する。
最初から世界全域や大艦隊を実装すると、交易と補給の調整前に制作量が膨らむため、初期版で航海の循環を成立させてから広げる。

仮題、登場人物、地名、組織名は本企画のために設定した名称である。
正式名称の採用には、先行作品と商標の確認を行う。
本書の数値は実装に使う初期設定であり、プレイテストによって調整する。

| 項目 | 採用方針 |
| --- | --- |
| 中心体験 | 海図に見つけた次の目的地へ、自分で準備して帰還する |
| 対象 | PCとスマートフォンのブラウザで遊ぶ一人用ゲーム |
| 操作 | 自動航海を基本に、手動操舵と帆の調整を選べる |
| 一回の遊び | 10〜20分でも一航海と成長を経験できる |
| 初期版の目標 | 第一章を40〜60分程度で遊び切り、その後も交易できる |
| 完成版の目標 | 五海域を巡る主筋を6〜10時間程度で体験できる |
| 公開形式 | 引き続き index.html 一ファイルで実行可能にする |
| 運営 | 初期版はログイン、通信対戦、課金、外部AI呼び出しを設けない |

既存の「自由航海」はタイトル画面から引き続き選べるようにする。
冒険モードでは所持金や物語を保存し、自由航海では天候や位置を自由に変更できる。
両モードの状態と保存領域を分け、自由航海での操作が冒険の進行に入り込まないようにする。

現行の三本マスト船は上位船として活かす。
序盤の小型船は同じ Builder による独自の船体と一〜二本マストの形状を追加し、見た目と能力の成長を一致させる。
単に三本マスト船の能力だけを小型船扱いにする状態は、最初の試作までに限定する。

## 3 権利関係と独自制作の方針

### 3.1 学ぶ対象と独自に作る対象

文化庁は、単なる事実やアイデアなどと、著作権で保護される著作物を区別している。[R1]
本企画では、探索と成長の循環、港間の価格差、補給、船員の役割といった設計上の考え方を抽象化して参考にする。
人物の設定、台詞、事件の順序、画面の構成、地図の図案、絵、曲、プログラムは独自に制作する。
複数の要素を組み合わせた結果の類似も確認し、「名前を変えればよい」という運用にはしない。

| 対象 | 本企画での扱い | 制作ルール |
| --- | --- | --- |
| 探索と船の成長 | 設計原則として参考にする | 数式、報酬、導線を独自に組む |
| 港間の交易 | 一般的な遊びとして採用 | 商品、在庫、価格変動、費用を独自設定 |
| 港への投資 | 施設と信用を育てる遊びへ変更 | 交易占有率の再現を目標にしない |
| 物語の収集目標 | 潮流観測と航路復元にする | 既存作品の固有の証、謎解き、イベント列を移さない |
| キャラクター | 全員を新規設定 | 名前だけでなく容姿、来歴、関係を独自に作る |
| UIと海図 | 現行の海と計器の表現を発展 | 参考作品の画面をトレースしない |
| 船と旗 | 帆船という題材を独自の形状で描く | 市販ゲームのモデルや紋章を抽出しない |
| 音と画像 | 自作または利用条件が確認できる素材 | 動画や攻略サイトから切り出さない |
| 実在地名と歴史 | 将来採用する場合は事実と図案を分ける | 初期版は架空世界で統一する |

コーエーテクモの「動画画像投稿ガイドライン」は、対象ゲームのプレイ動画や画像の投稿条件を定めるものと確認した。
本企画では、新作ゲームへの画像、音、人物、物語の転用許諾として扱わない。[R2]
無料公開や趣味制作でも、第三者の素材を使用する根拠と条件を記録する。

### 3.2 名称と公開時の表示

ゲームのタイトル、ロゴ、ストア説明、サムネイルは独自の作品名で統一する。
「大航海時代」のシリーズ名を自作ゲームの題名や派生作品を示す表示に使用しない。
設計検討で作品名に言及する場合も、公式の続編や公認作品を示す表現を避ける。

正式名称の決定前に、J-PlatPat で表記、読み方、類似表記、関連する商品と役務を確認する。
特許庁は商標検索の方法を公開している。[R3]
本書は「黒潮の航海」および副題について、商標上の使用可能性を確定するものではない。
特許と不正競争の論点は著作権と別に扱い、新規性のある特徴的な仕組みや商用展開の前に追加調査を行う。
名称やUIの変更だけで他の権利の問題が解消されると判断しない。

### 3.3 素材管理

公開する素材ごとに、asset_id、作者、入手元URL、取得日、ライセンス名、改変内容、必要な表示、証拠の保存先を記録する。
自作素材には制作日と元ファイルを記録する。
コードと文章、絵、音の利用条件を分けて明示し、公開リポジトリに置くことと利用許諾を混同しない。

外部素材は CC0 または再配布と改変の条件が扱いやすいものを優先するが、実際の利用条件を素材ごとに読む。
クレジットを表示するだけで、必要な許諾やライセンス条件を代替できるとは考えない。
現段階では、新たな第三者素材の採用と OSS ライセンスの決定を行わない。

生成AIで人物画や音を作る場合も、既存ゲームの画像や音を入力して似せる工程を採用しない。
生成指示、サービスとモデル、生成日、人による修正、類似性の確認結果を記録する。
文化庁が整理する生成物の類似性と依拠性の論点を踏まえ、AI生成だけを安全性の根拠にしない。[R4]

公開前に、作品名、人物、事件列、画面、素材、音、依存コード、宣伝表示を一覧で確認する。
判断がつかない素材は除外または差し替え、必要に応じて権利者の許諾や専門家の確認を得る。
ここで定めるのは制作上の運用基準であり、個別の侵害有無についての確定的な法律判断ではない。

## 4 世界観とゲーム固有の特徴

舞台は、大きな海流の変化によって遠方との航路を失った架空の海「巡環海」とする。
島々はそれぞれに交易品と生活を持ち、商会は安全な航路の情報を商売の資産として抱えている。
海賊も商船も、食料、船の傷み、天候を無視して遠くへは行けない。

プレイヤーは港の雑用で暮らしていた若い船長で、名前と外見の簡単な設定を選べる。
育ての親である船長イオは、十二年前に潮路の調査から戻らなかった。
主人公はイオの古い小型船「凪灯号」と、読めない潮の記録を受け取り、海へ出る。
生い立ちは共通の導入とし、その後の行動で商人、探検家、海賊の役割が育つ。

本作の固有の特徴は、発見した航路の情報を誰と共有するかによって、海の使われ方が変わることである。
測量情報を港へ公開すれば航路の危険が減り、補給や交易の選択肢が増える。
商会へ独占的に渡せば大きな報酬と優遇を受ける代わりに、他勢力との信用が下がる。
自分で保持すれば秘密の航路を使えるが、航路の維持と護衛を自分で負担する。

この仕組みは第二海域以降に実装する。
初期版は灯台の再点灯によって一つの航路が安全になるところまでを体験させ、完成版で選択肢を広げる。
プレイヤーの行為が地図上の線、港の景観、噂、予報に反映されるようにする。

## 5 主要人物と勢力

### 5.1 船で暮らす仲間

| 人物 | 役割 | 個人的な目的 | 物語での働き |
| --- | --- | --- | --- |
| セナ | 航海士 | 家族が住む霧の海への道を探す | 潮の記録を読み、遠方の行き先を示す |
| ガロ | 砲手 | 商会の護衛を辞めた過去を清算する | 襲撃と護衛の双方の選択を支える |
| ミナ | 船医 | 島々へ薬草を運べる航路を作る | 救助依頼と航海中の負傷を扱う |
| トト | 料理人 | 故郷の果実を他の港へ届ける | 食料の工夫と交易品の噂を伝える |
| ルカ | 測量士 | イオの観測を再検証する | 海図の記録と探索地点を担当する |

仲間は主人公に目的地を強制せず、現在の海域で実行できる案を提案する。
性格と能力は一対一に固定せず、例えば砲手にも安全な逃走策を話させる。
第一章ではセナとルカを物語の会話に登場させ、能力と雇用の仕組みは第二段階で有効にする。

### 5.2 航路を巡る勢力

自由港評議会は、各港が補給と交易の道を共同で維持する組織である。
会計官ノエは灯台の再建を依頼するが、港ごとの意見が異なり、全港を一つに従わせる組織ではない。

白帆商会は、予報と護衛を提供して交易を成長させた商会である。
代表ヴァルドは、潮路情報を管理しなければ事故と争いが増えると考えている。
交易経路の競争相手になると同時に、共同事業の相手にもなれる。

灰湾船団は、商会の通行料から逃れてきた船長たちの集まりである。
船長アデルは秘密の補給地を持つが、仲間の一部は無差別な略奪を行っている。
プレイヤーの悪名と、灰湾船団からの信用は別に計算する。

沿岸警備隊は港ごとの治安契約に基づいて活動する。
通商を襲った船を追う一方、救助や敵船への対応ではプレイヤーと協力することもある。
悪名が上がっても、すべての港が同時に入港拒否する状態にはしない。

## 6 主筋と第一章の物語

### 6.1 導入の場面

雨の翌朝、主人公は碧の群島の「灯待ち港」で、整備を終えた凪灯号を受け取る。
船倉には少しの食料があり、イオの航海帳には、同じ島の輪郭が異なる位置に何度も描かれている。
セナは書き込みを見て、「島は動かない。動くのは、ここを流れる潮」と説明する。
最初の航海の目的は、近隣の港へ木材を運ぶか、自分で仕入れて売るか、湾内を調べるかから選ぶ。

出港を選ぶと、画面の長い説明を閉じ、船と水平線を見せる。
主人公の名前を含む文章以外は、会話全文を新規に書き、既存作品の台詞を下敷きにしない。
導入を閉じても、目的と操作は航海帳から確認できる。

### 6.2 第一章の進行条件

主目標は、霧峰灯台を修復し、群島北部の潮の記録を得ることとする。
「灯台の位置」「修理資材」「潮の読み方」の三つをそろえると調査航海へ出られる。
各条件には複数の入手方法を設ける。

| 条件 | 主な達成方法 | 代替方法 |
| --- | --- | --- |
| 灯台の位置 | 三つの港で噂を聞き、見取り図を得る | 霧峰を直接探索して位置を発見する |
| 修理資材 | 木材を八単位持ち込み、40Gを支払う | 木材輸送の依頼を終え、港の支援を受ける |
| 潮の読み方 | 二つの観測点を調べる | ルカの測量依頼を一件終える |

灯台への航海前に、推奨する船体HP、食料、帆を表示する。
推奨未満でも出港を選べるが、危険の説明と退避港を確認できる。
灯台に着くと修理と観測をまとめた短い選択式イベントを行い、潮の記録を一度だけ獲得する。

帰還すると、北向き航路が海図に現れ、ノエが調査報酬80Gを支払う。
白帆商会から「遠方の調査を支援する」という誘いが届き、自由港からは航路を共同利用する提案が来る。
第一章の終了画面では、見つけた港、交易利益、救助、船の改造を振り返り、続けて自由に遊べる。

### 6.3 完成版の海域ごとの展開

| 海域 | 中心となる問題 | 記録を得る方法 | 得られる航海の変化 |
| --- | --- | --- | --- |
| 碧の群島 | 灯台が止まり、北の航路が不明 | 修理と近海観測 | 第一の潮路を海図に記録 |
| 赤砂沿岸 | 商会が通行料と水場を管理 | 共同交易、契約交渉、秘密湾の測量 | 遠洋航海の補給地点が増える |
| 雨帆諸島 | 季節風で往路と復路が変わる | 救助、護衛、風待ち観測 | 季節ごとの到着予測が使える |
| 霧鏡海 | 過去の海図と現在の潮が食い違う | セナの故郷の記録、海峡探索、取引 | イオの航海の経緯が分かる |
| 星灯列島 | 復元した潮路の管理を巡って対立 | 航路試走と最終交渉または海戦 | 最終航路と結末を選ぶ |

各海域の記録は、戦闘を経ずに得られる方法を少なくとも一つ用意する。
襲撃によって資金や情報を得る道も残し、物語の進行に特定の職業を必須としない。
サブ依頼には期限があっても、主筋には取り返せない時間制限を置かない。

### 6.4 真相と結末

イオは、潮の変化そのものと、商会が隠した航路の両方を調べていた。
観測記録は安全な海を保証する魔法の道具ではなく、各島で残されていた水位と風の記録だった。
遠方で救助した人々の記録をつなぐと、イオが船を失った後も島で暮らし、調査を続けていたことが分かる。
終盤でイオを救出する出来事を置くが、彼を仲間として雇わなくても結末へ進める。

最終的に復元した潮路について、プレイヤーが管理の方法を選ぶ。
過去の行動は提示される条件と港の反応に影響し、結末の選択自体は最後の画面で行う。

| 結末 | 選択 | クリア後の遊び |
| --- | --- | --- |
| 開かれた航路 | 観測結果を港へ公開する | 共同事業と新しい交易依頼が増える |
| 海を結ぶ商会 | 航路の管理と護衛を契約する | 施設運営と 他の商会との競争を続ける |
| 名もなき船長 | 記録を保持し、独立して航海する | 秘密航路と海賊依頼を利用できる |

結末は一つを正解として評価せず、交易、発見、影響力、悪名を航海記録に併記する。
エンディング後もセーブを継続し、世界を航海できる。

## 7 遊びの循環と目標の提示

短期目標は、港へ到着する、商品を売る、噂の島を見つけるという一航海の単位にする。
中期目標は、船の改造、船員の加入、灯台の修理、ライバルとの関係変更にする。
長期目標は、複数海域を巡る潮路の復元と、航路をどう使うかの決定にする。

港では「儲かりそうな品」「まだ確かめていない噂」「仲間の依頼」を最大三件提示する。
必須クエストだけを並べず、どの行き先を選んでも一定の成果が得られるようにする。
未知の港の位置を確定情報として先に表示せず、噂は範囲と手掛かりを示す。

一航海では、出港準備、海図で目的地選択、移動、遭遇や発見、入港、売却と補給、成長の順に遊べる。
探索で得た航路や知識を、次の交易と移動の費用に反映させる。
例えば、灯台が動くとその海域の遭難リスクが減り、食料の予備を減らして遠くへ行ける。

初回は敵襲や嵐を強制せず、第一の入港と売却を保証する導入条件を設ける。
船を改造した直後には、以前より遠い行き先の噂を出す。
すべての強化を所持金だけで説明せず、補給能力と到達できる港の増加も表示する。

### 9.2 未探索領域

海図上では、未知の海を暗い青、噂のある範囲を薄い輪郭、確認済みを通常表示にする。

船が移動した線分に沿って半径36ゲーム海里を開き、静止中は海図を広げない。

噂だけでは正確な港名や在庫を明かさない。
港を見つけると位置、訪れると相場とサービス、調査すると航路の情報が分かる。
海図の霧はUIで表現し、3Dの水平線に見える島を黒い幕で消す処理は行わない。

P1の海図は64ゲーム海里ごとのチャンクに分け、各チャンクを8×8のセルとして管理する。
セル辺長は8ゲーム海里になる。
保存はチャンクごとの64ビットの記録を16桁の16進文字列に変換し、JSONで扱う。
海域名と負の座標を含むキーの規則を固定する。

### 9.3 航海帳

航海帳には発見、噂、売買記録、依頼、主筋、仲間の目的を記録する。
追跡する目的は一つ選べるが、他の目的へいつでも切り替えられる。
相場は最終確認日を示し、未訪問の港の正確な売値を保証しない。
価格の履歴は直近十件までとし、セーブの容量を増やし続けない。

## 10 航海と補給の仕様

### 10.1 初期状態

| 項目 | 初期値 | 備考 |
| --- | --- | --- |
| 所持金 | 100G | 初回の交易に使う |
| 船体HP | 100 | 上限100 |
| 食料 | 30 | 初期上限30、商品船倉とは別枠 |
| 商品船倉 | 20単位 | どの商品も一単位で一枠 |
| 一般船員 | 8人 | P1は固定、賃金を別請求しない |
| 標準巡航速度 | 6ノット相当 | 風と帆で変化し、P2以降は積載も影響 |
| 発見済み | 灯待ち港と出港付近 | 相場は出発港のみ確認済み |
| 悪名 | 0 | P2から変化させる |

P1では食料代に一般船員の通常の維持費を含める。
P2の専門船員は雇用料と日ごとの賃金を追加する。
二重に維持費を請求する仕様にしない。

### 10.2 時間と距離

ゲーム内一日を、速度1倍の実時間60秒に設定する。
ゲーム海里は架空世界の距離単位として用い、表示には「ゲーム内換算」と記す。
現行の描画座標を1852で割る距離表示は、そのままゲーム進行の距離として使わない。

ロジックはゲーム海里とゲーム内時間で管理し、描画では一ゲーム海里を40座標単位に変換する。
6ノット相当の船は一ゲーム日で144ゲーム海里進む。
港間240ゲーム海里の穏やかな直行航海は、食料や積載の補正がない条件で約100秒になる。
これらは演出の設定で、現実の船の速度と地理を正確に再現するものではない。

```js
gameDays += realSeconds * speedMultiplier / 60;
distanceNm = speedKnots * 24 * deltaGameDays;
renderX = logicalXNm * 40;
renderZ = logicalZNm * 40;
```

実時間、ゲーム内時間、波や帆の表示時間を別々に扱う。
時間倍率は1倍、2倍、4倍とし、遭遇、危険、入港の手前で1倍へ戻す。
倍速でイベント判定や食料消費を飛ばさない。

P1では風による係数を0.7〜1.15、帆の係数を0〜1として、標準船速に掛ける。
潮の係数、損傷、食料不足、士気、航海士の補正は、それぞれの条件を満たすときだけ掛ける。
航路の標準所要時間と初回収支の検算は、風と帆の係数がともに1の条件で行う。
P2の積載係数は 1 - 0.10 * 積載率 とし、満載時は10％減速する。

嵐による損傷は、一ゲーム日あたり 8 * 帆の係数 * 嵐の強度 とする。
嵐の強度は0〜1で、にわか雨の遭遇と重なった間は大きい側の損傷だけを適用する。
天候の切替候補は二ゲーム日ごとに評価し、一日前から予報を表示する。
初回入港までの導入では嵐を発生させず、灯台修理の主筋に必要な観測を悪天候待ちで閉じない。

### 10.3 食料と航続距離

一般船員八人の消費は、一ゲーム日につき食料四単位とする。
食料は内部で小数として管理し、表示は小数第一位、購入は一単位ずつにする。
消費が端末のFPSで変化しないようにする。
「上限まで補給」は不足量を小数のまま補い、費用だけを切り上げる。
例えば不足量が6.67なら、補給後の食料は上限30、支払額は7Gになる。
通常の数量指定では上限を超える購入を受け付けない。

```js
foodPerDay = 4 * crewCount / 8 * cookFactor;
remainingDays = food / foodPerDay;
safeRoundTripNm = speedKnots * 24 * remainingDays / (2 * 1.3);
```

safeRoundTripNm は、帰路を往路と同じ距離とし、30％の予備を加えた出港判断用の目安である。
初期船の目安は約415ゲーム海里の片道距離となる。
実際の出港画面では登録された帰還港までの経路と風を使い、食料予測を計算する。
風待ち、損傷、積載によって距離が変わるため、確定的な到達保証として表示しない。

食料が切れると船速を標準の60％、一日につき士気を8低下させ、船体HPを4低下させる。
即座の全滅にはせず、補給地や救助の余地を残す。
港の買付画面では、次の目的地と帰還港に必要な食料を先に確保できる。

### 10.4 船体と天候

船体HPが35未満になると船速を20％下げ、入港時に修理を提案する。
船体HPが0になったら遭難処理へ移り、描画だけを止めて進行を続ける状態を残さない。
港の修理はHP一点につき1G、食料は一単位1Gを初期設定とする。
通常の港メニュー操作はゲーム時間を止め、修理の確定時に0.25ゲーム日を進める。
港内の食事と停泊は一日6Gで精算し、船内の食料を消費しない。

冒険モードの天候は予報と世界時間で変化する。
帆を絞れば嵐による損傷を減らせるが速度が下がる。
第一航海は穏やかな風とし、以後の嵐は予兆を表示する。
嵐をランダム遭遇と毎秒の損傷の両方で重複計上しない。

### 10.5 出港と入港

出港時に食料、HP、船倉、目的地、到着予測、予報を一画面で確認する。
発見済みの港を選ぶと、港の到着点までの安全な経路を提案する。
主航路は配置データで指定し、未知の地点は沖の目標点として探索航海を行う。
自動操舵が20秒間ほとんど進めなければ止めて、経路再選択と手動操舵を提示する。

港の到着点から12ゲーム海里以内へ入ると速度を落とし、2ゲーム海里以内で入港ボタンを有効にする。
入港の確定後は船の移動とゲーム時間を止め、港画面を開く。
接近しただけで港メニューが突然開く挙動を避ける。

## 11 交易と価格の仕様

### 11.1 五商品の価格

以下は在庫が標準値にあるときの基準価格であり、実際の売買価格は手数料と在庫で変わる。
食料と修理資材の購入は専用サービスとし、食料を商品として買い占めて売る処理はP1に入れない。
第一章へ持ち込む木材は、この表の木材商品を使用する。

| 港 | 木材 | 青染料 | 香草 | 鉄材 | ガラス |
| --- | --- | --- | --- | --- | --- |
| 灯待ち港 | 4 | 13 | 33 | 20 | 19 |
| 松帆港 | 10 | 20 | 26 | 10 | 24 |
| 青染港 | 8 | 8 | 22 | 23 | 29 |
| 雨凪港 | 12 | 16 | 10 | 21 | 35 |
| 硝砂港 | 15 | 24 | 20 | 27 | 12 |

全商品に標準在庫100単位を設定し、在庫は0〜200の範囲にする。
木材を灯待ち港で仕入れて松帆港へ、鉄材を松帆港で仕入れて灯待ち港へという往復が、最初の判断になる。
近海に分かりやすい利益を置き、遠い港では高利益の商品や観測の報酬を用意する。

### 11.2 在庫による価格変化

価格は在庫の不足で上がり、供給によって下がる。
売買の途中で在庫が変わるため、一括の取引も一単位ずつ同じ計算を積み上げる。
UIに表示した合計額と、確定時の引落額を同じ関数で算出する。

```js
scarcity = clamp(1 + 0.6 * (100 - stock) / 100, 0.65, 1.60);
mid = basePrice * scarcity * demandFactor;
ask = Math.ceil(mid * 1.05);    // プレイヤーの購入単価
bid = Math.floor(mid * 0.95);   // プレイヤーの売却単価
```

この式は価格の考え方を表す。
実際の金額精算では在庫と需要倍率を整数で保持し、最後に一度だけ切り上げまたは切り下げる。
需要倍率は80〜125の整数パーセントとし、二進小数の誤差で価格が1G変わることを防ぐ。

```js
scarcityMilli = clamp(1000 + 6 * (100 - stock), 650, 1600);
numerator = basePrice * scarcityMilli * demandPercent;
ask = Math.floor((numerator * 105 + 9999999) / 10000000);
bid = Math.floor(numerator * 95 / 10000000);
```

demandFactor は通常1、需要イベント時は0.8〜1.25で変える。
イベントの終了後は世界時間の更新で基準へ戻す。
一回の売買では需要倍率を固定し、各単位の確定後に在庫を一単位増減させる。
再入港だけで在庫や需要イベントを初期化しない。

購入前に資金、空き船倉、在庫を確認する。
売却前に所有数量と港の在庫上限を確認する。
成立できる数量と総額を示し、数量を黙って変更して決済する処理を避ける。
同一港で購入直後に同量を売る行為が利益にならないことを、全商品と在庫の範囲で検証する。

### 11.3 市場の回復と契約

世界時間が一日進むと、特産品の在庫は最大15単位、その他は最大8単位、標準100へ近づく。
「一日待つ」は港で6Gを支払って時間を進める行為とし、メニューを開いたまま無償で市場を回復させない。
海上で待つ場合は食料と専門船員の賃金を消費する。

依頼は配送、救助、測量の三種から始める。
一つの依頼は一度だけ精算でき、未達の配送品を売った場合は依頼を進められない。
初回配送は木材四単位を契約品として預かり、松帆港で40Gを受け取る。
契約品は商品船倉を使い、自由交易用の木材と識別する。
導入を拒否しても、自分の資金で交易と探索を進められる。

### 11.4 初回交易の検算

灯待ち港と松帆港の木材在庫を100、需要倍率を1とし、十二単位を購入して松帆港で売る条件を計算した。
在庫の変化を含む購入総額は 60G、売却総額は 105G、交易粗利益は 45Gとなる。
240ゲーム海里を6ノット相当で航海すると、食料消費は約6.67単位であり、同量補給の費用相当を引いた利益は約38.33Gとなる。
食料を上限まで補給する費用を7Gとして精算すると、食料は30、所持金は138Gになる。

この検算は穏やかな直行航海と通常相場での初期値確認である。
損傷、積載による減速、専門船員の賃金、帰路の費用は含まない。
実装後は往復、需要イベント、遭遇を加えて収支と所要時間を確認する。

## 12 船の成長と船員

### 12.1 五段階の船

段階は、同じ船を強化する第一海域の成長指標とする。
完成版では船体の購入も用意するが、P1は改造の確定処理と見た目の変化に絞る。
各段階の値は基本値であり、帆、積載、専門船員の補正を別に適用する。

| 段階 | 到達費用 | 船倉 | 食料上限 | HP上限 |
| --- | --- | --- | --- | --- |
| 1 沿岸船 | 初期 | 20 | 30 | 100 |
| 2 補強沿岸船 | 120G | 28 | 45 | 115 |
| 3 遠航船 | 追加300G | 40 | 65 | 135 |
| 4 武装帆船 | 追加700G | 56 | 90 | 160 |
| 5 長航海船 | 追加1400G | 76 | 130 | 190 |

| 段階 | 標準船速 | 砲撃能力 P2 | 見た目の変化 |
| --- | --- | --- | --- |
| 1 | 6.0 | 4 | 小型の一〜二本マスト船 |
| 2 | 6.3 | 5 | 船体の補強と補給樽 |
| 3 | 6.8 | 6 | 船体と帆面積の拡大 |
| 4 | 7.2 | 8 | 現行の三本マスト船と砲門 |
| 5 | 7.6 | 10 | 大きな船倉と航海装備 |

改造時に貨物と食料を増やさず、上限のみを上げる。
HPは上限増加分だけを加算し、既存の損傷を無料で全回復させない。
第一章は段階2または3を推奨し、段階5をクリアの必須条件にはしない。

帆、船倉、砲、計測器の装備はP2で分岐を追加する。
大型船があらゆる面で最良にならないように、上位船ほど旋回を遅くし、船員数と維持費を増やす調整はP3で行う。
P1の五段階は、その調整を行う前の単純な成長方式とする。

### 12.2 船員の役割

| 役割 | 標準能力 | 雇用料 | 一日賃金 | 加入のきっかけ |
| --- | --- | --- | --- | --- |
| 航海士 | 自動航海速度を8％上げる | 60G | 1G | 近海の観測依頼 |
| 砲手 | 命中率を10ポイント上げる | 80G | 2G | 護衛依頼 |
| 船医 | 負傷による稼働低下を30％減らす | 70G | 1G | 救助依頼 |
| 料理人 | 食料消費を15％減らす | 60G | 1G | 香草の配送 |
| 測量士 | 海図の確認半径を20％広げる | 70G | 1G | 新しい島の調査 |

P2は専門船員を二人まで配置し、同じ役割を重ねて能力を加算しない。
専門船員も乗船人数に数え、食料を消費する。
役割の効果は自動で適用し、能力の有無によって主筋を完全に閉じない。
P3以降で配置上限を三人に増やし、上位船や船員個別の依頼を追加する。

賃金は小数を蓄積し、一日単位で精算する。
未払いは借金として記録し、一日につき士気を5下げる。
未払い三日で専門船員を休職させるが、その人物が持つ主筋の情報は航海帳に残す。
港で支払えば再配置でき、人物の消失による進行不能を防ぐ。

士気は0〜100で、食料、敗北、救助、休息で変化する。
低士気では船速と命中率を最大15％下げる。
人物別のイベントは、必要な加入フラグと完了フラグで管理する。

| e_current | 有利な流れ | 流れに乗るまたは針路維持 | 0.4日だけ船速15％増 |
| e_squall | にわか雨 | 帆を絞るまたは維持 | 絞れば遅延、維持ならHP5〜10減 |
| e_reef | 浅瀬の兆し | 迂回または慎重に通る | 迂回なら距離増、通過はHP損傷の可能性 |
| e_supply | 漁師の船 | 食料を買うまたは通過 | 食料を最大5、単価2Gで購入 |
| e_ruin | 小島の標識 | 調べるまたは通過 | 観測の手掛かりと一回限りの発見報酬 |
| e_rumor | 帆船の使い | 話すまたは通過 | 未訪問の港や一時需要の噂 |
| e_damage | 帆索の緩み | 応急修理または次港へ | 食料1または0.3日だけ船速10％減 |
| e_patrol | 沿岸警備の船 | 連絡または通過 | P1は情報、P2は悪名に応じた対応 |

遭遇の評価は累積移動距離が120ゲーム海里進むたびに行い、該当候補から30％の確率で一件選ぶ。
前回の遭遇から0.5ゲーム日が経過していることを条件にし、一入港間の遭遇は最大二件にする。
条件に合う候補がなければ何も起こさない。
漂流物を静止して待ち続けるだけで獲得できる方式にはしない。

地点固有の観測、財宝、救助報酬には恒久IDと回収済みフラグを付ける。
一般的な遭遇は再発できるが、同じ海図記録や報酬を重複取得させない。
選択肢を開いている間はゲーム時間を止め、閉じる直前に一度だけ結果を確定する。

### 13.2 商船への対応

P2では商船を見つけたとき、船型、見える積荷、護衛、所属、危険度を示す。
隠れた積荷は噂や追跡で分かるようにする。
選択肢は交易、護衛の提案、追跡、襲撃、通過の五つとする。
追跡は半日までで食料を消費し、同じ商船から無限に情報報酬を受け取れない。

襲撃は商品を無償で得られる可能性があるが、損傷、弾薬費、悪名、信用低下を伴う。
獲得できる数量は船倉と敵の積荷で制限し、満載分を通貨へ自動変換しない。
奪った品には stolen と被害勢力を記録する。
通常港の買取価格は通常の70％、灰湾の港は95％を初期値とし、高悪名では通常港の取引条件も悪化する。

### 13.3 悪名と信用

| 悪名の範囲 | 表示 | 主な変化 |
| --- | --- | --- |
| 0〜19 | 普通の船長 | 通常の入港と取引 |
| 20〜49 | 襲撃船として知られる | 検問と価格の不利が増える |
| 50〜79 | 追跡対象 | 沿岸警備との遭遇が増える |
| 80〜100 | 大きな賞金首 | 安全な港と敵対勢力が分かれる |

民間商船の襲撃で悪名を15、警備船への襲撃で20上げる。
救助で2下げ、一ゲーム日に自然減少する値は最大0.5とする。
同じ救助IDの繰返しと、罰金だけによる即時の完全解消を認めない。

勢力の信用は -100〜100 とし、悪名とは別に保存する。
例えば悪名が高くても灰湾から信頼される状態、悪名が低くても白帆商会と競合する状態を作る。
初期港と灰湾の避難港は、救助後の最低限の補給と船の回復を利用できるようにする。

### 13.4 簡易海戦

海戦は三〜六ターンの選択式とし、既存の3D船を背景演出に使う。
プレイヤーが毎ターン選ぶ行為は、砲撃、回避、接近、逃走、降伏とする。
一般遭遇の一戦を実時間60〜90秒以内に収めることを目標にする。
P2で複数船の直接操作を加えない。

```js
hitChance = clamp(0.55 + gunnerBonus - evasionPenalty, 0.15, 0.90);
damage = Math.max(1, cannonPower + roll(1, 4) - enemyArmor);
escapeChance = clamp(0.45 + 0.04 * speedDifference, 0.20, 0.85);
```

砲撃一回につき弾薬費を2G支払い、払えなければその選択肢を無効にする。
八ターン続いたら互いに離脱し、一般遭遇が無期限に続くことを防ぐ。
決着時の戦利品、損傷、悪名、経験は一度だけ確定する。
敗北後も物語を進められるようにし、最終海戦には交渉または秘密航路の代替手段を設ける。

## 14 港の施設と影響力

P3では、港に倉庫、灯台、補給桟橋を整備できるようにする。
施設は投資額だけで支配を決めるものにせず、商品や観測情報の提供も進行条件にする。
他勢力が強い港でも、別の施設や依頼を通じて関係を改善できる。

| 施設 | 初期費用 | 資材 | 効果 |
| --- | --- | --- | --- |
| 倉庫 | 200G | 木材6 | 港に商品を20単位保管できる |
| 灯台 | 300G | 木材8と鉄材4 | 接続航路の危険イベント率を20％下げる |
| 補給桟橋 | 250G | 木材10 | 食料の補給価格を15％下げる |

P3では施設効果を所有者と共同事業の参加者に適用し、航路情報を公開した灯台は全船へ効果を広げる。
倉庫の保管品にも取得元を残し、盗品の属性を洗い落とす処理にしない。
施設は上限を決め、同じ投資を繰り返して能力を無限に上げない。

港での支持点は、施設の実績、直近三十日の正味供給、依頼の実績、信用から作る。
同じ港で買って売っただけの循環を、供給実績へ重複計上しない。

```js
support = facilityPoints + deliveryPoints + servicePoints + trustPoints;
influencePct = 100 * support / (100 + sumAllFactionSupport);
```

facilityPoints は上限100、deliveryPoints は上限40、servicePoints は上限30、trustPoints は0〜30にする。
信用の値は (trust + 100) * 0.15 で trustPoints に変換する。
分母の100は港の独立した住民の支持分であり、全勢力の支持が0でも計算できる。
影響力60％以上で主要な協力勢力として表示するが、港そのものを消去や占領の対象にはしない。

海域の主要協力勢力になる条件は、五港中三港で影響力40％以上を保ち、共同航路を一件運用することとする。
この中期目標は主筋クリアの必須条件にしない。
ライバルは三ゲーム日ごとに予算内で行動し、プレイヤーの未訪問港に無制限の投資をしない。
第一海域では主要な潮路が見つかるまで、初期港の協力関係を強制的に奪わない。

## 15 画面と操作の仕様

### 15.1 航海画面

船と水平線を画面の中心に保ち、所持金、食料、HP、目的地を確認できるようにする。
速度と風の既存表示は残し、細かな数値は詳細パネルへまとめる。
画面に常時出す目標は一つ、重要通知は一件にする。

PCでは海図と航海情報を左右に置き、船を隠さない下部に操舵と帆を配置する。
スマートフォン縦画面では、上部に所持金とHP、下部に操舵、海図は折り畳みで表示する。
相場、依頼、船員は同時に小さく並べず、底面パネルを切り替えて開く。

### 15.2 港画面

タブは市場、造船所、桟橋、酒場、航海帳、出港とする。
P1では船員の配置を表示せず、酒場は噂と物語を担当する。
売買は数量、単価の範囲、総額、売買後の資金と船倉を一画面で示す。
不足理由は「資金不足」「船倉満杯」「在庫不足」を具体的に表示する。

港の施設投資や船員の雇用は確定前に費用を示す。
出港時は食料を推奨量まで買う操作を設け、その価格を確認できる。
未探索へ向かう航海では、距離予測が不確かなことを表示する。

### 15.3 海図と遭遇画面

海図は港、島、噂の範囲、危険海域、航路、船を別の記号で描く。
色だけで識別せず、形と文字の説明を付ける。
未知の海にも目標点を置けるが、未発見の陸地に正確な港への自動到着は設定できない。

遭遇画面では、何を発見したか、見えている危険、選択肢の費用を短い文章で示す。
襲撃の決定だけは、対象勢力と予測悪名を再確認する。
会話を閉じても内容は航海帳へ残し、誤タップで手掛かりが消えない。

### 15.4 入力と利用しやすさ

主なボタンは44×44 CSSピクセル以上にし、キーボードで選択できる。
既存の矢印キー、WASD、帆、Pによる停止を引き継ぐ。
冒険モードでRは位置の即時リセットを行わず、港への救助かタイトルへ戻る操作に置き換える。
新規ゲームによる保存の上書きは明示してから確定する。

文字の基準は本文14〜16ピクセルとし、重要な資源を小さい装飾文字にしない。
船の揺れを減らす設定と、音量の調整を用意する。
WebGLを利用できない場合は対応状況を説明し、保存データの書き出しを利用できるようにする。

## 16 保存と失敗後の復帰

### 16.1 保存の対象

保存するのは、モード、版、世界のseed、乱数の現在状態、ゲーム日、位置、船、資源、貨物、発見、依頼、船員、勢力、施設、市場、物語のフラグとする。
最後の安全な港、賃金の未払残高、報酬の取得済みID、食料やイベントの小数累積も保存する。
描画用のメッシュ、WebGLオブジェクト、航跡、カメラ補間の途中値は保存しない。
選択中の遭遇は遭遇IDと決定前の状態を保存し、読込みで乱数を再抽選しない。

自動保存は入港、取引、改造、物語報酬、遭遇確定後に行う。
航海中は三十秒ごとに保存する。
書込みを連打せず、dirty の変更だけをまとめて処理する。

P1は localStorage を使用し、直前の正常なセーブを別キーへ残す。
schemaVersion と worldVersion を付け、版が変わったら移行処理を通す。
形式不明のデータを黙って新規ゲームで上書きしない。
容量上限に近づく拡張では IndexedDB へ移行するが、P1から複数の保存方式を併用しない。

### 16.2 端末と公開先

GitHub Pages、ChatGPT Sites、ローカルのHTMLは保存領域が同一とは限らない。
別の公開先や別端末へ移るため、JSONの書き出しと読込みをP1の必須機能にする。
保存できないブラウザ環境では、その場で通知して書き出しを案内する。
書き出しファイルには外部へ送信する情報や認証情報を入れない。

読込みではファイル容量、版、数値の範囲、恒久ID、数量と船倉の整合を確認する。
文字列をHTMLとして挿入せず、プレイヤー名やログは textContent で表示する。
JSONには実行コードを含めず、eval を使わない。
一人用の保存データの編集を完全に防ぐ仕組みは、初期版の目標にしない。

### 16.3 遭難と再出発

遭難したら最後の安全な港へ戻り、所持金の20％と通常貨物の30％を失う。
金額と数量は切り上げ、所持量を上限として控除する。
物語の記録、発見、船員、船の段階は残す。
契約貨物は失敗として依頼を閉じ、同じ依頼を再受注できる条件を港で示す。

救助後は船体HPを上限の35％、食料を12単位にする。
資金も売却できる品もない場合、初期港の短い手伝いを一回実行して20Gを得られる。
この手伝いは資金と売却可能貨物がともにない救済条件に限定し、時間を消費する。
HPや食料を無制限に増やす無料サービスにはしない。

## 17 実装構造と既存コードの移行

### 17.1 一ファイルの中の責務

配布物は index.html 一ファイルを維持する。
内部は次の責務に分け、港画面のクリック処理から資源を直接書き換える構造を避ける。
初期版ではビルドツールと新しい描画ライブラリを導入しない。

| 区分 | 管理対象 | 主な処理 |
| --- | --- | --- |
| Content | 港、島、商品、船、遭遇、物語 | IDで参照する定数データ |
| GameState | 資源、進行、市場、発見 | 保存可能な論理状態 |
| Sailing | 位置、航路、風、衝突 | 時間と距離の更新 |
| Economy | 売買、補給、改造、契約 | 検証と一括確定 |
| Events | 遭遇、依頼、会話、結末 | 条件判定と一度だけの報酬 |
| Renderer | 海、船、島、海図 | 状態を読み取り、表示する |
| UI | パネル、入力、通知 | コマンドをゲーム処理へ送る |
| Persistence | 保存、移行、書出し | 検証と正常版の保持 |

ゲーム状態は START、SAILING、PORT、ENCOUNTER、BATTLE、RECOVERY、ENDING に分ける。
PAUSED は各状態に対する停止フラグとして持つ。
状態ごとに受け付けるコマンドを決め、港外からの売買や戦闘中の改造を拒否する。

### 17.2 現行処理の変更

update(dt) は操舵と描画の更新を分け、ゲーム内時間を使う固定刻みの処理へ移行する。
drawChart() は発見データを読み、未探索の島を確定情報として描かない。
islandSpecs はIDと海域を持つ内容データへ移す。
visited は一時的な描画オブジェクトから保存可能な発見データへ移す。

既存の random() は島の外観に使っているため、ゲーム進行用の乱数と分離する。
地形の装飾、遭遇、戦闘、市場の乱数を別々のストリームで管理する。
画質や鳥の数を変えても遭遇や戦利品が変わらないようにする。

WebMCPの set_voyage_controls も、画面と同じモード判定を通す。
冒険中の weather と timeOfDay の変更は受け付けず、読取と操舵に必要な操作を残す。
保存や主筋の報酬を直接操作する入口を公開しない。
未対応ブラウザでもゲームが動くように、WebMCPを必須条件にしない。

### 17.3 更新刻みと性能

航海ロジックの固定刻みは速度1倍の実時間で0.05秒とする。
倍速は時計へ倍率を掛けるだけでなく、通常刻みのサブステップを増やして処理する。
衝突は移動前後の線分で確認し、低FPSや倍速で島を通り抜けないようにする。
入港と遭遇が同じ更新で発生した場合は、遭難、入港、物語、一般遭遇の優先順で一件を確定する。

画面が非表示になったら航海と音を止め、復帰時に非表示の経過時間を進行へ加えない。
WebGLコンテキストが失われた場合は状態を保持し、復元できるときに描画資源を作り直す。
復元できなければ保存書き出しと再読込みを案内する。

スマートフォンで30FPSを目標とし、海面の格子、島の詳細、DPRを画質設定で下げられるようにする。
海域に入っている島だけを描画するだけでなく、不要なメッシュを解放してから次の海域を生成する。
初期版は一海域のみをメモリに置く。
読み書きとレイアウト計測を毎フレーム繰り返さず、HUDは変更時または毎秒五回程度に更新する。

初期版の性能目標は本体1MB以内、保存1MB以内、標準的なスマートフォンで操作に対する長い停止がないこととする。
ファイル容量と保存容量は外部素材を増やす前に確認する。
これらは未測定の目標値であり、実機測定後に端末名、ブラウザ版、FPS、読み込み時間を記録する。

## 18 データの定義例

以下は新規ゲームの保存形式の例である。
実装では内容データと表示文を別に定義し、人物名や地名の変更が保存IDを変更しないようにする。

```json
{
  "schemaVersion": 1,
  "worldVersion": "azure-1",
  "mode": "adventure",
  "phase": "PORT",
  "worldSeed": 726199,
  "rngStates": {"encounter": 17, "combat": 31, "market": 47},
  "clock": {"gameDays": 0, "speedMultiplier": 1},
  "player": {"name": "船長", "gold": 100, "infamy": 0},
  "ship": {
    "id": "ship_nagito", "tier": 1,
    "hp": 100, "food": 30, "crewCount": 8,
    "cargo": [], "officers": []
  },
  "position": {"regionId": "azure", "xNm": 0, "zNm": 0},
  "portId": "p_light",
  "discovery": {"ports": ["p_light"], "fogChunks": {}},
  "quests": {},
  "storyFlags": {},
  "factions": {},
  "markets": {},
  "completedRewardIds": [],
  "pendingEncounter": null
}
```

港の market は商品IDごとに stock、demandFactor、lastUpdatedDay を持つ。
新規ゲームでは全港を初期化し、未訪問港も世界時間で在庫を更新する。
上の markets の空オブジェクトは、読込み時の新規初期化を示す省略形である。

貨物は goodId、qty、originPortId、paidGold、stolen、victimFactionId、contractId を持つ。
同じ商品でも契約品と盗品は通常貨物に混ぜない。
qty は正の整数とし、船倉を超える保存データを受け付けない。

依頼は id、type、status、objective、reward、rewardClaimed を持つ。
status は AVAILABLE、ACTIVE、READY、COMPLETED、FAILED とする。
主筋の条件はIDとフラグの組み合わせで記述し、イベント処理へ実行用コードを埋め込まない。

## 19 制作順序と完成判定

### 19.1 最初の縦断試作

最初に作るのは、灯待ち港と松帆港だけを往復し、木材を売買し、食料を補給して、段階2へ改造できる試作とする。
物語の会話と多数の島を増やす前に、価格、時間、移動、補給、保存が一続きで動く状態を作る。
この試作に触れて、航海中に次の目的が欲しくなるか、補給が作業になりすぎていないかを判断する。

### 19.2 開発の作業単位

| 作業 | 主な成果 | 完了条件 |
| --- | --- | --- |
| M0 | モードと状態の分離 | 自由航海、再起動、描画が従来どおり動く |
| M1 | 二港と入出港 | 手動と自動で確実に到着できる |
| M2 | 木材の交易と補給 | UIの合計額と精算、食料消費が一致する |
| M3 | 改造と保存 | 改造して再読込みしても成長を保持する |
| M4 | 五港と未探索海図 | 発見と相場情報の範囲が一致する |
| M5 | 十遭遇と第一章 | 代替手段から灯台を修理し、帰還できる |
| M6 | 船員と海賊行為 | 交易と襲撃に異なる収支と関係変化がある |
| M7 | 施設と二海域 | 港の変化が航路と交易に反映される |
| M8 | 五海域と結末 | 全主筋と三結末、版の移行を確認する |

M0〜M5をP1として公開し、M6以降は版を分けて追加する。
一作業ごとに変更をレビューして記録し、次の大きな要素を同時に入れない。
この段取りは実装量の見通しを立てるためのもので、工数や完成日の保証にはしない。

コードの変更を始める前に、現在の公開版へ戻せる基準点を残す。
開発中の画面で確認してから GitHub Pages と Sites の公開版へ反映する。
公開先ごとに保存移行と読込みを確認し、公開URLが同じでもセーブ形式の変更を見落とさない。

### 19.3 仕様変更の扱い

商品価格、距離、船、報酬、食料消費は内容データの定数へ集約する。
仕様を変えたら変更理由、遊びへの影響、保存互換性を記録する。
第一章の目標とP1の範囲を増やす変更は、実装前に本書も更新する。
気づいた改善をすべて初期版へ入れず、航海の循環を改善するものから選ぶ。

## 20 検証と公開基準

### 20.1 数値と状態の確認

| 検証 | 条件 | 合格基準 |
| --- | --- | --- |
| 取引 | 全商品、在庫0〜200、通常需要と端点需要 | 資金、在庫、貨物が保存則を満たす |
| 即時往復売買 | 同港で購入後に売却 | 正の利益が生じない |
| 総額の一致 | 1、12、20単位の注文 | プレビューと実際の精算が一致する |
| 過剰注文 | 資金不足、満載、港在庫不足 | 状態が部分的に変更されない |
| 時間倍率 | 同じseed、経路、入力列を1、2、4倍で実行 | 同じゲーム内経過時間で消費とイベント評価が一致する |
| 停止 | 港、会話、背景タブで停止 | 意図しない時間、食料、負傷の進行がない |
| 報酬 | 同じIDのイベントを再実行 | 二重に資金や記録を獲得しない |
| 保存 | 取引、遭遇前後、改造後 | 再読込みの状態と乱数が一致する |
| 破損データ | 未知の版、負の数量、巨大ファイル | 正常な保存を残して読込みを拒否する |
| 救済 | 資金0、食料0、HP0、港と敵対 | 再開可能な行動が残る |

### 20.2 実際の遊びによる確認

P1では、初見の利用者が説明をすべて読まなくても、五分以内に入港と一回の売買を経験できることを目標とする。
十五分以内に最初の改造または明確な探索成果を得られるか確認する。
第一章では位置の噂、木材輸送、自力調査の各経路を通して完了できるか確認する。

P2では、交易中心、探索中心、海賊中心の三つの遊び方で、維持費と成長の速度を比較する。
海賊行為が毎回最も儲かる状態、近海の一往復だけで全成長が終わる状態を修正する。
損傷や悪名を強めすぎて再開できない状態にもならないようにする。

試遊後に聞く内容は、「次に行きたかった場所」「帰還する理由が分かったか」「困ったときに選べる行動があったか」「同じ操作が続きすぎた箇所」とする。
達成率と時間は少人数の試遊でも記録し、印象だけで難度を変えない。
初期版にはアクセス解析を必須とせず、同意を得た試遊記録で改善する。

### 20.3 公開する条件

PCとiPhoneの主要ブラウザで、初回起動、タッチ操作、回転、停止、再開、保存、書き出しを確認する。
オフラインで一ファイルを開いた場合にも、外部アクセスなしで主要機能が動くことを確認する。
画質を下げても戦利品や相場が変わらないことを確認する。

作品名と素材の確認、出所記録、ライセンス表示を終えた版を公開する。
公開に残る不具合は、遊びと保存への影響を具体的に記録する。
進行不能、二重報酬、保存消失、資源の負値、到達できない港は公開前に修正する。

## 21 後回しにする機能

P1ではオンライン対戦、サーバー保存、ランキング、課金、巨大な実在地図、歩行探索、複数船の自律運営を入れない。
船員の文章を都度生成するAI、音声会話、日替わり生成クエストも初期版の完成条件にしない。
実装と権利確認、保存、ゲーム調整の量が増え、現行の一ファイルで遊べる利点が薄れるためである。

完成版の後で、大艦隊、自分の港、地中海や日本を含む別の世界設定を検討する。
架空世界から実在地理へ変更する場合は、距離、船速、季節、地図素材の権利を改めて定義する。
本書のゲーム海里を実在の海里として読み替えるだけの拡張にはしない。

## 22 開発着手時の判断

着手する範囲はM0〜M3の二港試作とする。
「木材を運び、利益を出し、補給し、船を改造し、保存して再開する」という一続きの体験を最初の確認対象にする。
それが成立したらM4とM5を追加し、灯台の修理で終わる第一章を公開できるゲームにする。

物語の主筋と五海域の設定は、初期版を作る間も固定の目安として使う。
追加する港、仲間、装備には、それによって新しく選べる航海を一つ以上対応づける。
航海の目的が増えない要素は、制作順位を下げる。
